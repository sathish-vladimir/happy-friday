## 1. Tech Stack & Packages Used

| Package | Why it's used |
|---|---|
| `flutter_riverpod` | State management across the whole app (required by the assignment; used exclusively — no `setState`-based business logic, no other state library). |
| `firebase_core` | Initializes Firebase in `main()` before the app runs. |
| `firebase_auth` | Email/password authentication (register, login, logout, session identity). |
| `cloud_firestore` | Remote data store for user profiles and app content (`users`, `featured_album`, `popular_meditations` collections). Chosen over Realtime Database for its richer querying and document model, which fits the profile + content structure here. |
| `shared_preferences` | Lightweight local key-value store for session hints: `is_logged_in`, `uid`, `email`. Lets Splash decide Login-vs-Home instantly without waiting on a network call. |
| `sqflite` | Local SQL cache for home-screen content (`featured_album`, `popular_meditations`), so the Home screen can still render the last-known content if Firestore is unreachable (offline-first fallback). |
| `image_picker` | Native gallery picker for the profile photo during registration. Configured to only ever open the gallery (never the camera) with `maxWidth`/`maxHeight`/`imageQuality` set, which — combined with modern Android's Photo Picker / iOS's PHPicker — means **no runtime storage/photos permission is required at all**. |
| `just_audio` | Audio playback for meditation tracks (play/pause/resume/stop, position stream) from the Home mini-player. |

> No `firebase_storage` is used anywhere in this project (see the "Firebase Setup" and "Assumptions" sections below for why).

## 2. Architecture

The project follows a **feature-first, layered (data / presentation) structure**,
close to clean architecture, without introducing a full domain layer where it
wasn't needed for an app this size (see Assumptions):

```
lib/
├── main.dart                     # Firebase init + ProviderScope root
├── main_screen.dart              # Bottom-nav shell (Home / My Albums / Playlist / Profile)
├── firebase_options.dart         # Generated by flutterfire configure
│
├── core/
│   ├── local/app_preferences.dart      # SharedPreferences session wrapper
│   ├── database/app_database.dart      # sqflite schema + singleton instance
│   ├── providers/firebase_providers.dart  # FirebaseAuth / FirebaseFirestore instances
│   ├── services/audio_player_service.dart # just_audio wrapper
│   ├── theme/app_colors.dart           # Centralized color tokens (no hardcoded colors in screens)
│   ├── utils/responsive_extension.dart # .w / .h / .sp / .r sizing extensions (no hardcoded pixel values)
│   └── widgets/app_bottom_nav_bar.dart # Shared bottom navigation bar
│
└── feature/
    ├── auth/
    │   ├── auth_dependency_injection.dart   # Riverpod wiring for this feature
    │   ├── data/
    │   │   ├── model/app_user_model.dart        # uid, email, profileImageBase64
    │   │   ├── source/auth_remote_source.dart   # Firebase Auth + Firestore calls
    │   │   └── repo/auth_repository.dart        # Orchestrates source + local session
    │   └── presentation/
    │       ├── view/ (splash_screen, login_screen, register_screen)
    │       └── view_model/auth_view_model.dart  # AsyncNotifier<AppUserModel?>
    │
    ├── home/
    │   ├── home_dependency_injection.dart
    │   ├── data/
    │   │   ├── model/ (featured_album_model, meditation_model)
    │   │   ├── source/ (home_remote_source → Firestore, home_local_source → sqflite)
    │   │   └── repo/home_repository.dart   # Remote-first, falls back to local cache on failure
    │   └── presentation/ (home_screen, home_view_model, widgets)
    │
    ├── profile/        # Reads the logged-in user's live profile (see below)
    ├── settings/        # Account settings + logout
    ├── my_albums/       # Static UI screen matching the Figma "My Albums" tab
    └── playlist/        # Static UI screen matching the Figma "Playlist" tab
```

Each feature keeps its own `data` (model/source/repo) and `presentation`
(view/view_model/widgets) layers and its own dependency-injection file, so
features stay independent and easy to navigate. `core/` holds only things
genuinely shared across features (theming, sizing, local storage, Firebase
instances, audio playback).

### Why this over a strict domain/data/presentation split?

The assignment allows either — a strict 3-layer clean architecture, or a
"clean-architecture-preferred" approach appropriate to project size. Given
the 12-hour timeline and the fact that models here map almost 1:1 to
Firestore documents with no complex business rules to isolate, an explicit
`domain` layer (use cases + entities separate from models) would have added
boilerplate without real benefit. Repositories already provide the
abstraction boundary between data sources and the UI/state layer.

## 3. State Management (Riverpod)

- **`AsyncNotifierProvider`** for anything with a loading/success/error
  lifecycle: `authViewModelProvider` (login/register), `homeViewModelProvider`
  (fetching featured album + meditations).
- **`Provider`** for stateless dependencies/services: Firebase instances,
  repositories, `AudioPlayerService`.
- **`FutureProvider`** for one-shot reads that the UI just needs to watch:
  `currentUserProfileProvider` — fetches the logged-in user's Firestore
  document (email + profile picture) for the Profile and Settings screens.
- **`StateProvider`** for simple local UI state shared across a screen (e.g.
  `currentlyPlayingProvider` for the mini-player).

`ref.watch` is used in build methods to react to state; `ref.read` is used
inside callbacks (button presses, etc.) to avoid unnecessary rebuilds.

## 4. Authentication & Onboarding Flow

```
Splash
  │
  ├── checks AppPreferences.isLoggedIn() (local, no network call)
  │
  ├── true  → Home (MainScreen)
  └── false → Login
                ├── Login success  → Home (session saved locally)
                └── "Register" link → Register
                        ├── Creates Firebase Auth user
                        ├── Optionally picks + encodes a profile photo
                        ├── Saves profile doc to Firestore (`users/{uid}`)
                        ├── Signs back out (see Assumptions)
                        └── Returns to Login with a confirmation message
```

- **Session persistence**: on successful login, `uid`, `email`, and an
  `is_logged_in` flag are saved via `SharedPreferences`. Splash reads this
  flag to decide where to route on cold start, without waiting on Firebase.
- **Logout**: Settings → LOGOUT tile → confirm dialog → `FirebaseAuth.signOut()`
  + `SharedPreferences.clear()` → navigates to Login, clearing the whole nav
  stack so the back button can't return to authenticated screens.
- **Profile picture (no Firebase Storage)**: the picked image is resized to
  512×512 and compressed to quality 70 via `image_picker`, then base64-encoded
  and stored directly as a field on the user's Firestore document. This keeps
  the whole project on Firebase's free Spark plan (Storage requires the
  billed Blaze plan) while still avoiding a broken image-upload experience.
  See "Known Limitations" for the trade-off this involves.

## 5. Local Storage Strategy

| Data | Where | Why |
|---|---|---|
| Login/session flag, uid, email | `SharedPreferences` | Tiny, synchronous-feeling reads needed on every cold start (Splash routing). |
| Featured album + popular meditations | `sqflite` | Structured, larger, queryable content that should survive being offline; `HomeRepository` always tries Firestore first and only reads the local cache if that fails. |
| Profile photo | Firestore (`users/{uid}.profileImageBase64`), not local | It's per-account data that should follow the user across devices, not stay device-local. |

## 6. Firebase Setup

1. Create a Firebase project in the [Firebase Console](https://console.firebase.google.com).
2. Enable **Authentication → Sign-in method → Email/Password**.
3. Enable **Cloud Firestore** (start in production/locked mode — rules are below).
4. Run `flutterfire configure` from the project root and select the project;
   this generates `lib/firebase_options.dart` (already present in this repo,
   but you'll need your own if you fork this to a different Firebase project).
5. Add the required Firestore security rules (Console → Firestore Database → Rules):

   ```
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {

       match /users/{userId} {
         allow read, write: if request.auth != null && request.auth.uid == userId;
       }

       match /featured_album/{docId} {
         allow read: if true;
       }

       match /popular_meditations/{docId} {
         allow read: if true;
       }
     }
   }
   ```

   - `users/{uid}`: a signed-in user may only read/write their **own** document.
   - `featured_album` / `popular_meditations`: public read-only app content,
     seeded manually in the Firestore console for this assignment (see
     Assumptions — there's no admin/CMS screen to write these).
6. No Firebase Storage setup is needed — this project intentionally doesn't use it.

## 7. Running the Project

```bash
flutter pub get
flutterfire configure   # only if using your own Firebase project
flutter run
```

If you add or change any native plugin (like `image_picker`) and it doesn't
seem to work, do a full stop + `flutter clean` + `flutter pub get` + fresh
`flutter run` — hot reload/restart does not re-register native plugin
channels.

## 8. Completed Features

- Splash screen with local-session-based routing (no unnecessary network wait).
- Firebase Auth register/login with validation (email format, password length).
- Firestore-backed user profile (email + base64 profile photo), created at
  registration and read back by both Profile and Settings screens.
- Native gallery image picking for the profile photo, permission-free on
  modern Android/iOS.
- Logout flow with confirmation dialog, full session clear, and nav-stack reset.
- Home screen: featured album + popular meditations, fetched from Firestore
  with automatic fallback to a local sqflite cache if offline.
- Audio playback (play/pause/resume) for meditation tracks via `just_audio`.
- Bottom navigation shell across Home / My Albums / Playlist / Profile.
- Consistent theming (`AppColors`) and responsive sizing (`AppResponsive`)
  used throughout instead of hardcoded values.
- Loading / error / empty state handling on the screens backed by real data
  (Home, Profile) via `AsyncValue.when`.

## 9. Known Limitations

- **My Albums and Playlist screens are UI-only** — they replicate the Figma
  layout (filter chips, card grids) but aren't yet wired to Firestore or a
  view model; their data is static/mock. Given the assignment's 12-hour scope,
  effort was prioritized on the auth flow, Firestore integration, and
  offline-caching pattern, which the evaluation criteria weight most heavily.
- **No dedicated onboarding carousel screens.** The assignment permits
  designing onboarding based on your own understanding of the product flow —
  here, "onboarding" is treated as the Register flow itself (collecting
  email, password, and an optional profile photo) rather than a separate
  swipeable intro sequence, since the Figma file didn't include one.
- **`featured_album` / `popular_meditations` content is seeded manually** in
  the Firestore console rather than through an in-app admin flow, since the
  assignment scope is the mobile app, not a CMS.
- **Profile picture size ceiling**: because it's stored as base64 inside the
  Firestore document, it's capped (512×512 @ quality 70) to safely stay under
  Firestore's 1 MiB per-document limit. A production app with heavier images
  would need Firebase Storage (or another object store) instead — this was a
  deliberate trade-off to keep the project on Firebase's free tier for this
  assignment.
- **Registration signs the user out and returns to Login** rather than
  auto-entering Home, by design choice (an explicit login step after signup),
  not a bug.
- Minor duplication: `firestoreProvider` is declared in both
  `core/providers/firebase_providers.dart` and
  `feature/home/home_dependency_injection.dart`. Both point to the same
  `FirebaseFirestore.instance`, so it's functionally harmless, but should be
  consolidated to the `core` version in a follow-up cleanup pass.

## 10. Assumptions Made

- Onboarding status/logic is represented by whether a Firestore user profile
  document exists and whether a local session is saved — no separate
  "onboarding complete" flag was introduced, since the Figma didn't specify
  additional onboarding steps beyond account setup.
- Cloud Firestore was chosen over Realtime Database since the assignment
  allowed either, and Firestore's document/collection model maps more
  naturally onto "one profile document per user" and "one collection per
  content type."
- Firebase Storage was deliberately avoided (billing requirement); the
  profile-photo-as-base64-in-Firestore approach is an explicit, documented
  substitution for it.
- Where the Figma design didn't specify exact copy/behavior for a settings
  item (e.g. "Delete Account & Data"), the tile is present visually to match
  the design but not yet functionally wired, since deleting a Firebase Auth
  user safely requires re-authentication handling that was out of scope for
  this pass.
